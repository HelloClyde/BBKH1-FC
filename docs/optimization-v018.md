# 0.1.8：PPU、无事件执行区间和存储音频恢复

本轮以用户的《三国志 II》日志为依据。正常版与诊断版日志均有持续欠载；
诊断版两个同步存档分别约 637 / 587 ms，超过 256 ms 预充，甚至超过 512 ms 播放环。
诊断版还记录了 864,038 次背景刷新细分计时，计时器读取本身会影响结果。
因此分开处理核心计算、存储边界和测量开销，不用加大缓冲掩盖持续供给不足。

## 执行和正确性边界

1. PPU：仅在跳过颜色输出、没有精灵零候选、没有 Mapper/高清包观察者的普通背景路径中，
   聚合早期 CHR/nametable 内存读取。最后四次 fetch 保留，完整 32 位移位寄存器、属性锁存、
   横向滚动地址和输出指针保持一致。精灵求值、状态位、纵向滚动、Mapper hook 和 IRQ 不省略。
   有像素消费者时，仍执行原始路径。
2. JIT：在现有无事件证明成立的连续纯指令段内，把 PC/PI 留在寄存器，到返回处统一提交；
   删除必被操作数覆盖的 opcode DB 写入。任意指令前缀结束时均提交准确状态；保留每条指令的
   CPU 预算检查，以及 DMC/APU/IRQ、内存映射、代码失效和回退边界。本轮没有扩大无事件假设。
3. 存储：先同步核心保存区并检查完整 CRC。未变化时不预充、不停音、不写文件；有变化时
   先停止音频设备并取消循环描述符，再做同步 IO。写完保留重采样相位，从新 PCM 重新预充，
   128 个输出样本淡入，短暂跳过显示帮助恢复高水位。保存头和数据合成一次 firmware write，
   仍保留双槽、关闭重开、CRC、完整回读与逐字节检查。包括 Mapper 19 的 128 字节 IRAM，
   全部 8320 字节均参与判脏和保存。成功日志留在内存，暂停/退出后落盘。
4. 诊断：每 31 帧才细分 PPU 计时，跨 300 帧记录窗口连续轮转。使用质数周期避免固定锁定
   2/3/6 帧显示节奏。其余帧只读采样标记，省去每次背景刷新两次高频计时。
   正常版本编译移除该标记和计时分支。

存档期间游戏仍同步停顿并静音，旧排队 PCM 会被丢弃。这里修复的是重复旧声音和恢复失步，
并没有消除磁盘写入延迟。保留 `AUDIO_STORAGE pauses/raw_ticks/max_raw_ticks` 供复测；
原始 tick 只记录计数，不依据旧函数名假定其频率是 80 Hz。

## 音频为什么不能直接通用 HLE

FC 的 APU 是寄存器控制的声波发生器，游戏自己的音乐驱动运行在 6502 上。
游戏直接写音色、频率、音量、波形/采样等寄存器，没有所有游戏都调用的统一“播放歌曲”接口。
H1 的 PCM 播放已经交给原生音频设备；需要模拟的是产生这些 PCM 的 APU 行为。

不需要每条 CPU 指令都生成声音。可按寄存器写入的时间戳、帧计数器事件、DMC DMA/IRQ
等边界补算和批量混音；事件之间无需重复执行完整调度。但 DMC 会占用 CPU 时间，APU/Mapper
可以触发中断，不能只生成听起来类似的声音而丢弃这些影响。特定游戏音乐引擎的 HLE 可以另做，
却不适合作为通用 NES 核心的替代。本版继续使用事件边界和精确区间计算。

参考：[APU 寄存器](https://www.nesdev.org/wiki/APU_registers)、
[按需同步](https://www.nesdev.org/wiki/Catch-up)、[DMC DMA](https://www.nesdev.org/wiki/DMA)。

## 测量解释

《三国志 II》对比 0.1.7，使用最终 0.1.8 普通版二进制：

| 场景 | 基线指令量 | 本版指令量 | 减少 |
| --- | ---: | ---: | ---: |
| 128 帧核心，每 6 帧显示 1 帧 | 282,634,210 | 238,228,247 | 15.71% |
| 600 帧完整应用，有声标题 | 1,982,253,797 | 1,973,455,795 | 0.44% |
| 1800 帧完整应用，新游戏/城市命令 | 6,191,078,113 | 6,086,409,214 | 1.69% |

核心差分包括完整序列化状态、PCM 和视频逐帧一致；该跳帧场景中背景函数自身减少 57.21%。
600 帧完整应用还验证了实际播放环字节一致。
1800 帧的源 PCM、核心状态和最终存档一致，但两次存档会清空旧播放环并重新预充，
显示帧数从 1790 变为 1740，所以 1.69% 包含显示和音频缓冲策略变化，不能全算作核心加速。
13 个 LCD 差异均有实际未刷新的观察证据；没有把静止画面 hash 相同推断为“跳帧”。
旧版缺失的前缀显示标记通过相同二进制、ROM、输入和时钟重放补齐，前 1219 帧核心/PCM/LCD
逐帧相同；重放不收集指令成本，原始 1800 帧成本完整保留。场景覆盖全国地图、城池和命令菜单，
不包含战斗。

所有 MIPS 指令量由实际 BDA 执行统计，固件服务在该比较中使用相同 mock；它不是物理 H1
时钟周期或 FPS。核心固定跳帧差分与包含存储/显示策略变化的完整应用比较分别记录。
本轮使用的私人游戏 ROM、固件及《三国志 II》的截图、音频仅留在本地验证目录，不进入安装包。

诊断日志的 `ppu_background_sampled` 只包含采样帧，不能当成全程 PPU 成本。
`core_cpu_and_unsampled_ppu` 包含未采样 PPU 和其他核心工作，不能叫作纯 CPU/JIT 开销。
`PROFILE_SAMPLING` 分别给出 detail/light 帧数、显示帧数和核心均值；不将采样耗时盲目乘 31。
出现 `PROFILE_BEGIN fault!=0` 时，不把该段高精度数据当成完整有效测量。

完整固件模拟中，普通版执行了两次自动存档并恢复音频，正常退出；音频接口错误和视频错误为 0。
诊断版验证了 31 帧采样，但首段在 TCU 回绕附近被保守读取检查拒绝；暂停恢复后的 291 帧段有效，
detail=10、light=281。该限制和失败尝试保留在验证记录中，没有用模拟器计时声称真机帧率提升。
