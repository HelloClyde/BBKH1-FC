# H1 真机完整 BDA 对照流程

发布范围：这是开发期本地流程，不是 v0.1.16 源码包的自包含复现指南。文中引用的特定设备热补丁、安装计划、`tests/diagnostic_firmware.py` 等私有实验入口及工作区外的调试器/固件工具不随本版分发；公开构建与 CI 不依赖它们。

本流程仅为离线准备，不代表已经测得性能改善。设备操作由持有 H1Debug 的一个会话串行执行。适用 H1/Y100 V1.41；遵循本机 `h1-debug` skill 和当前 `tools/h1_debug.py`，不将 RAM EXEC 模块当作 BDA 安装器。

## 先获得可用基线

现有 NES-D rev1 已能作为第一轮热点采集程序：从未加载用户存档的全新 ROM 运行 1500 帧，在 RAM 保存完整核心状态；每组恢复并核验状态，再运行 1800 帧，前 300 帧预热、后 1500 帧测量。每组重建 JIT 缓存和音频队列。跳帧 1、缩放 1、声音开启、音量 100，关闭自适应追加跳帧和存档读写。

它只支持以下已核验 ROM 内容，不能按“霸王的大陆”“三国志2”或文件名判定兼容：

| 项目 | 值 |
| --- | --- |
| 完整 ROM SHA256 | `7b4fcd1c0be33e69943dcf9c81cca67bac634a9de2881aa2f3d8f9b6a3864117` |
| PRG＋CHR MD5 | `de319a7a8099c388810c59cb038e8c9d` |
| Mapper | 19 |
| PRG / CHR | 262144 / 262144 字节 |

启动脚本为 `tests/scenarios/sgz2-newgame-city.json`。快照恢复后的第 1～4、121～124 帧按 A，然后无游戏输入。因此当前场景的准确名称是“城市进入＋停留”，不是持续的城市菜单操作。

开始优化前先用这轮数据确认计时是否可信、核心/PPU/调度/音频哪个部分占时、欠载是否与编译或其他事件重合。如果 TCU 校验失败，保留 RTC 粗吞吐和事件，不用无效细计时推断热点。RTC 有约 ±1 秒端点量化界；短组需要更长测量或重复，不能报告虚假的精度。

## 固定连续城市操作

1. 在相同 ROM 的城市快照上，用当前 480×272 截图识别菜单，先在测量外确认一段只打开/关闭菜单的 A/B 循环。不要盲点购买、结束回合或改变城市状态的选项。
2. 将确认的序列转成按 NES 帧编号的输入 mask，在 BDA 内执行；完整替换物理游戏输入。PC 的按键命令 ACK 只能证明接受输入，固定毫秒间隔也不等于固定游戏帧。
3. 保存脚本原文和 SHA256，记录起点/关键菜单的截图与完整序列化状态校验值。每组都从同一快照恢复；随机数、CPU/PPU/APU/Mapper、输入锁存、SRAM 均由完整状态恢复，不只恢复画面。
4. 相同输入在基线与候选上先验证核心状态和画面/PCM 一致性。菜单能返回原处不表示时间相关核心状态必须回到循环前相同 CRC；应比较两版在相同帧检查点的状态，而非错误要求循环前后 CRC 相同。
5. 若两版核心状态格式不同，先明确序列化兼容性；不能直接套用旧 `.st1` 文件。可以各自从同一新 ROM 和引导输入生成状态，然后核验逻辑等价性。任何一致性失败先处理，不把错误执行造成的变快算作优化。

第一轮可复用现有城市停留回放获得热点；新的城市操作回放需要完成上述验证后才进入主比较。

## 冻结基线与候选

为每版在 PC 的私有测试目录保留 BDA、对应 ELF、build.json、源代码版本及未提交补丁、构建参数、输入脚本和各文件 SHA256。BDA 的 SHA 必须与 build.json 相符；读取目标符号只使用该次构建对应的 ELF。旧日志、旧 ELF 和新 BDA 不混用。

两版使用相同编译器、优化选项、JIT 缓存大小、缩放/跳帧、PCM 采样率和音量、是否 HLE、采样模式及回放帧数。优化项以外的差异必须列出。正常 BDA、轻量诊断和细分诊断分别比较；不能用“正常基线＋细分候选”得出提速比例。

推荐三对重复，顺序 A/B、B/A、A/B。每次新建播放队列和代码缓存、恢复同一状态；预热和测量分开。需要区分冷编译与热运行时，另列冷段，不能把它混入预热后主结果。每次记录 resident image_id、USB 连接状态、原始计时口径；基线和候选保持一致。

测量窗口内不截图、不轮询状态、不读取大块 RAM、不运行 EXEC 微基准。前后台 H1Debug 驻留及 USB 连接本身是实验条件。控制和截图放在测量前后，避免把传输开销当作游戏热点。

## 安装与日志回收

现有 H1Debug 没有文件上传/下载 RPC。完整 BDA 只能通过普通磁盘复制，再从原生菜单启动。`EXEC` 的 ABI 用于 RAM 测试模块，不用于完整 BDA，也不通过 runtime_table 间接写 NAND 或安装文件。

CDC 调试设备为 `07C4:A4A6`；普通磁盘为 `07C4:A4A5`。不能假定端口是 COM4 或盘符是 F/G。确认实际设备和卷对应关系后才复制文件。`tools/install_h1_debug.ps1` 的“确认 USB 磁盘、写临时文件、读回 SHA、再替换”流程可以参考；该脚本安装的是 H1Debug 本体，不应拿它安装 NES。

当前 NES-D 每次启动都截断 `A:\FC\nesdiag.log`。仅把两个 BDA 改名不能隔离日志；仅给 A/B 各一个文件名也仍会覆盖同版的下一轮重复记录。因此有两种可行方式：

- **保持现有 BDA：** 每次完整运行后回收日志，再启动下一次。每轮都需要 CDC/磁盘切换。
- **一次安装、连续运行：** 先做独立的测试外壳修改，为每一次运行保留唯一日志，例如 A1/B1/B2/A2/A3/B3，或在单次 BDA 内按组记录所有重复。日志文件不得重新打开截断旧结果；启动、错误提示、build.json 和日志内版本标识同步更新。需要同时防止两版状态/配置路径冲突。这属于测试设施修改，完成校验后才能承诺只切换一次回收。

当前 NES-D 所有组禁止存档和配置读写，可以读取同一 ROM 而不改变用户存档。正常版测试会产生存档；应先备份相同 ROM 路径附属的整个文件集合，或明确使用私人测试 ROM 路径和私人存档副本。不要仅备份一个 `.sav`：本项目使用交替提交的 `.s0/.s1`，快捷状态还有 `.st1.s0/.st1.s1` 至 `.st3.s0/.st3.s1`，配置是 `.cfg.s0/.cfg.s1`，RTC 使用 `.rtc.s0/.rtc.s1`（实际存在时）。保留相应普通日志和被替换的程序。先复制到 PC 并核对哈希，再进行安装。

回收前让 BDA 正常结束并关闭日志文件。不要在程序仍在写盘时切换模式。回到普通磁盘后，将每轮日志、截图关联信息和输出文件复制到私有证据目录，核对复制前后的 SHA，保存文件列表。比对用户存档/配置与测试前的哈希；检查缺失与新建文件，不能只检查仍存在的文件。先保存证据，不自动恢复覆盖用户在测试期间合法产生的新进度。

H1Debug 可读取已识别且仍存活的 RAM，但当前 NES-D 的帧记录缓冲在退出时释放。不能在程序退出后凭旧指针把已释放内存当作日志下载；若将来增加 RAM 导出，需要明确的暂停边界、缓冲寿命和版本化长度/校验协议。

## 最少必须手工完成的部分

如果目标 BDA 已安装且 CDC 已连接，主任务可自动启动、输入、截图和测量，不需要为调用 skill 重装或关闭 H1Debug。

确实需要安装或回收文件时，PC 无法通过当前协议替用户完成物理拔插及调试器未连接时的菜单动作：

1. 主任务结束当前游戏并保存证据，正常停止调试器。按设备当前提示拔插 USB，使设备进入普通磁盘模式；COM 消失本身不等于磁盘已就绪。
2. PC 自动确认卷身份、备份、复制全部待测 BDA，并读回校验。安全弹出；用户拔线，在机器上启动 H1Debug、关闭启动提示并返回原生菜单，再插 USB。
3. 主任务重新发现当前端口并验证精确握手 `H1DEBUG/1 V1.41 RESIDENT`，持有一个 Client 完成连续测试。所有唯一日志都保留后，正常退出并停止调试器，用户再次拔插进入普通磁盘，PC 自动回收和分析。

如果需要更新 H1Debug 本体且本次开机已运行过旧驻留服务，要遵循其重启流程；一般 BDA 测试沿用兼容驻留服务，无须更新。测试结束应明确设备保留在 CDC 还是普通磁盘，不擅自改变用户仍需使用的状态。

## 可复用的现有代码

| 文件 | 用途与限制 |
| --- | --- |
| 工作区 `tools/h1_debug.py` | 唯一串行 Client、身份检查、按键、480×272 截图、已知 RAM 读取。不要自行改写串口协议。 |
| `src/platform/diagnostic_replay.c` | 纯帧调度、固定 mask、快照控制边界、15 组模式/采样安排。可扩展已验证的城市操作脚本。 |
| `src/app.c` 诊断 runner | 完整 BDA 的 RAM 快照、模式切换、音频重建、统计和中止路径。 |
| `tests/diagnostic_core_mips.py` | 状态恢复与三种 CPU 模式一致性验证；其模拟器内存地址不能照搬到真机。 |
| `tests/diagnostic_firmware.py` | 完整固件中的 BDA、日志及存档不修改检查。只验证流程正确性，不是真机测速。 |
| `tools/analyze_diagnostic.py` | 日志完整性、时钟有效性、PCM 控制、按组/采样统计；实机使用 `--source-kind device`。 |

分析主指标为相同测量段的 RTC 模拟 FPS、显示 FPS、音频缺口和重复范围；细分热点只使用有效细计时。帧记录 `loop` 是“输入至播放等待的处理段”，不含遥测整理，不能用其倒数当作完整应用 FPS。持续城市操作与城市停留分别列出。欠载与编译同帧只表示相关，必须控制变量复验后归因；不能仅凭 MIPS 指令数或 QEMU 速度宣布真机改善。
