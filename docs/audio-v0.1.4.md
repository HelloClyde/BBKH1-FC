# 0.1.4 持续欠载排查

用户反馈 0.1.3 仍断音。该日志记录 1086 个核心帧、54 次音频欠载、1064 个
音频追赶帧、377 个显示帧和零接口错误。说明最多跳 2 帧的显示策略仍未补足音频。
0.1.3 在电脑完整固件模拟器中零欠载的结果不能证明用户设备已经修好。

## 调整

- 背景像素对查找表仅在 16 个背景调色板字节实际变化时重建，比较时机仍在
  原来的优先级位设置之后，保留中途调色板写入及即时存档恢复。
- 对严格等于标准 `CartBR` 的读取处理函数直接读取当前 ROM 页；其他处理函数
  仍逐次调用，保留 mapper 的副作用和总线缓存。ROM 换页仍使用核心的 `Page` 表。
- 跳过显示的帧只省掉扫描线末尾的颜色及强调数据写入；背景取数、精灵评估与
  合成、精灵零号碰撞、CPU/APU 及 mapper 时序继续执行。光枪扫描钩子存在时禁用
  这条输出捷径。
- 核心混音率改为 22050 Hz，声明的 AV 采样率与核心 PCM 一致，通过连续相位重采样
  到 H1 的 32000 Hz 输出。降低采样率会减少高频细节，不改变游戏帧时序。
- 两次及以上欠载后，缓冲不足时允许最多跳 5 帧以降低显示成本；128 ms 待播量
  恢复后回到用户设置。这会临时降低画面帧率，不能弥补无限的核心算力不足。

## 检查范围

实际 MIPS 核心逐帧对比使用相同 ROM 与输入：同采样率的优化副本与 0.1.3 对比
PCM、完整即时存档和显示帧；最终 22050 Hz 版本则对比 CPU、PPU、RAM、保存区及
显示帧，音频持续时长按各自声明的采样率检查。改变采样率后不声称 PCM 逐样本相同。
控制流程中的 MIPS 翻译块指令条目减少，不能将这个比例当成真机速度提升。

原生差分测试另覆盖 30000 个调色板状态、300000 次标准及自定义处理函数读取，
包括 ROM 换页、处理函数替换、数据总线副作用与两种字节序。PCM 测试覆盖
22050/32000/48000 Hz 重采样、未读数据保护、两次欠载后的跳帧升级及存档预缓冲。
普通包的 MIPS 服务替身测试和诊断包的完整 V1.41/QEMU 测试分别记录 SHA-256。
所有 ROM、录音及固件只留在私有 `build/`。

## 设备诊断

诊断文件由 `python tools/build.py --profile` 生成 `dist/H1FC-profile.bda`。
`python tools/package.py --profile` 将其打包为 `dist/H1FC-profile-install.zip`，
安装路径仍为 `A:\应用\程序\H1FC.bda`。也可以只复制下面的单个 BDA。
将它复制为设备上的 `A:\应用\程序\H1FC.bda`，运行出问题的游戏约 20～30 秒后
正常退出，再读取 `A:\FC\h1fc.log`。

日志中的 `profile=1` 标识诊断包，`PROFILE_CLOCK` 表示 TCU5 校验是否成功。
`PROFILE_RTC_RUN` 给出独立 RTC 的帧数/时长，`PROFILE_COST` 区分背景绘制、
APU 帧末混音、显示输出、PCM 重采样、输入、存档及等待。`core_cpu_and_other_ppu`
包含 CPU 调度、逐指令 APU 事件和其他 PPU 工作；`apu_finalize` 不代表全部音频成本。
TCU 不可用时会停止精细计时，仍保留 RTC 帧数。暂停/退出恢复借用的 TCU5。
诊断会增加计时开销，其帧率不能直接等同于普通包。

0.1.4 尚未在用户设备复测。当前结果与限制见 `docs/evidence/audio-v0.1.4.json`。
